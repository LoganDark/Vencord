Feature ideas from a long patch-maintenance session (auditing and repairing ~8 Vencord plugins against Canary). Ordered by how much time each would have saved.

BIGGEST WINS

1. Test patches in Vencord's own syntax.
   test_module_patch takes raw regex, so every `\i`, `$self` and `#{intl::KEY}` had to be hand-expanded, and I wrote my own evaluate loop to run a plugin's finds across all modules. Wanted: a tool that takes {find, match, replace} exactly as written in a plugin (or a plugin name, to test its currently registered patches) and reports: which modules the find hits (loaded AND unloaded), match count per replacement, whether the patched source parses, and a short before/after snippet around each match. It should warn when a non-`all` find hits more than one module (found two such ambiguous finds by hand: NoTimestamps `showTimestampOnHover:` and ImplicitRelationships `GUILD_MEMBERS_REQUEST:`).
   Related papercut: test_module_patch echoes the full matched text and full replacement. For a patch that matches a whole function (6KB) that flooded the reply twice over. A truncation/context-chars option would help.

2. Report which patches actually applied in the running client.
   On a non-dev build there is no SYM_PATCHED_SOURCE / SYM_PATCHED_BY, and WebpackPatcher.patches empties as patches are consumed, so "did this patch apply?" could not be answered directly. I had to walk React fibers to find a live patched function and stringify it. Wanted: capture the patcher's "had no effect" / "errored" / "Undoing patch group" warnings at startup and expose them per plugin. A general console-log reader (filterable by logger name) would cover this too.

3. Search with context, not just module ids.
   find_modules_by_string / _by_regex return ids only. I repeatedly wrote evaluate scripts to get match counts plus surrounding text, and to check several candidate find strings for uniqueness in one go. Wanted: optional context snippets and per-module match counts, and multiple needles per call. Also: evaluate cannot see the unloaded-chunk index, so my hand-rolled uniqueness checks only covered loaded modules.

4. Reverse intl lookup.
   Given a hashed key (e.g. `t.J6STd9`) return the English message; given text (e.g. "Claim") return matching keys and the modules using them. I located a UI string by reading feature plumbing when a text search would have gone straight to it.

SMALLER THINGS

5. Reading big modules. Anything over ~80KB overflowed the tool result into a file that then had to be sliced with jq. Wanted on read_module_source: offset/length, "context around this needle", and "return the enclosing function at this offset / containing this string".

6. Importers and call sites. "Which modules import module X, under what local alias, and how do they call export Y" came up three times and was rebuilt by regex each time. Wanted: find_importers(moduleId, exportName?) returning call-site snippets.

7. Component tools. (a) Find mounted instances of the component whose source contains a string, returning a props summary, child tree and DOM labels. (b) Render a component offscreen in a detached root with given props and an error boundary, returning the resulting DOM summary. I built (b) by hand and it was what settled a "is the patch broken or is it the channel" question.

8. Privacy-safe previews. I wrote shape-only summarizers to avoid pulling the user's DMs, user ids and message content into the transcript, and still leaked some DOM text once through a careless selector. Wanted: a redacting preview mode (types/shapes/counts, no string values) for evaluate and inspect, ideally the default for store data.

9. Session handling. With two sessions connected (PTB + Canary) every call needed clientId. Wanted: a sticky default session, or selection by releaseChannel. Also a notice when a session's buildNumber changes mid-session (Canary updated once during the work) or when a client reconnects.

10. Refs. Nearly every evaluate was a one-shot read, so I was constantly calling release_ref. Wanted: an option for evaluate not to mint a ref (or auto-release).

11. Module diff across sessions. Comparing the same module/function between two connected sessions (e.g. PTB vs Canary), or against a cached copy from a previous build, would show exactly what changed when a patch goes stale.

12. Minor: evaluate's EVAL_FAILED message has no stack or line, so a `Cannot read properties of undefined (reading 'filter')` in a 30-line definition took a second call to locate.

Session context: checked ShowAllMessageButtons + MoreQuickReactions compatibility, traced why Discord opens /quest-home at startup, fixed patches in two userplugins (noNitroShopQuests, noClosingPrivateChannels). Two sessions connected (canary 678980, ptb 678976). Feedback, most valuable first:

1. Accept Vencord patch syntax directly. Every pattern passed to test_module_patch / match_module_source had to have `\i` hand-expanded to `[A-Za-z_$][\w$]*`, and `$self` hand-expanded to `Vencord.Plugins.plugins["Name"]`. That means the regex I tested is not the regex I then wrote into the plugin, so a transcription slip between the two goes untested. Running patterns through canonicalizeMatch / canonicalizeReplace (src/utils/patches.ts) inside the plugin would remove this. Intl keys (`#{intl::KEY}`) the same.

2. A tool that takes a whole Vencord patch ({find, replacement[]}) rather than a module id. It should resolve `find`, report how many modules it matches (uniqueness is a requirement for a find and I had to check it with ad hoc evaluate scans every time), then run the replacements. Ideally it could take a plugin name and test that plugin's patches as built.

3. Patch status for the live client. I could not see which plugins patched a module or whether a replacement had no effect. I guessed at `$$vencordPatchedBy` and got nothing; String(wreq.m[id]) returns the unpatched source. Dev builds already expose wpPatcher.getFactoryPatchedSource / getFactoryPatchedBy. Wanted: (a) per plugin, each patch's find result, target module and per-replacement effect, (b) a `patched: true` option on read_module_source / match_module_source. "Fix plugin X" would start from (a) instead of from reading the module.

4. Search across all modules with context. Most of my evaluate calls were hand-written `Object.keys(wreq.m).filter(...)` loops returning `.{0,200}needle.{0,200}` snippets, or AND-ing several substrings. A cross-module regex search that returns snippets with configurable context per hit (not just module ids), plus multiple needles with AND, would replace nearly all of them.

5. Fan out to all sessions. With two clients connected every call needs a clientId and I ran each check twice. An option to run on every session and report per-session results (or just "identical on all") would halve the calls.

6. test_module_patch output size. When a replacement matches a large span (a whole ~7KB function for ShowAllMessageButtons), the trial echoes the full `matched` and the full `replacement`, so ~14KB for a change of ~200 chars. A diff-style view (changed regions with some context) or a cap with an opt-in for the full text would help. With includeFinalSource on a 157KB module the reply was 172KB and overflowed the tool result limit; a hard cap or a "write to file and return the path" behavior would be safer than returning it inline.

7. evaluate ergonomics. (a) I passed previewLimits on almost every call; the 400-char default total is too small for the common case of returning collected snippets. For plain JSON-serializable results, returning real JSON (with a size cap) would be better than a truncated preview string. (b) Every call parks a ref even when only the preview is wanted; I left a dozen unreleased. An option not to park, or auto-release for plain data, would keep the registry clean.

8. Startup / reload investigation. There is no way to observe anything that happens before the plugin connects. I only confirmed the /quest-home redirect because window.navigation.entries() happened to retain it. Useful: a small boot-time buffer the plugin records before connecting (route changes, Vencord patch warnings such as "had no effect", console errors) that can be queried afterwards, and a reload tool that waits for the session to reconnect (gated on user approval) so a fix can be verified end to end. The persistent clientId across restarts worked well for this.

9. Server instructions get truncated by the client. The instructions block was cut off partway through the "Patch nodes" section, so anything after it never reached me. Shortening the instructions or moving detail into the tool descriptions would avoid that.

10. Lower priority: a helper to look up CSS rules for a class-name module (given a module id, return the rules whose selectors use its classes). I wrote a stylesheet walker by hand to learn what `nameplated` did.

What worked well: test_module_patch's parse check of the final source, match_module_source with groups and offsets, sessions reconnecting under the same clientId after a restart.
